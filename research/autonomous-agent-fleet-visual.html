Models behind LiteLLM (real config swap) · tools behind MCP · workers behind a common adapter interface (real work, not config).

Run the fleet only when work is parallel + well-specified + high-value. Otherwise one interactive agent is cheaper. The dial opens as your eval earns trust.

The one truth that shapes everything

This is not a swarm

Empirical, load-bearing

Software engineering is a poor fit for naive breadth-first parallelism. Coding has fewer truly parallel tasks than research, agents still coordinate poorly in real time, and multi-agent systems burn ~15× the tokens of a chat interaction. So the winning shape is a thin deterministic control plane driving a small number of strongly-isolated, single-threaded workers, coordinated by the dependency structure of the work and by git isolation — not twenty agents loose on a repo.

The composition

A (default spine) + G (reliability, always at L3+) + H (verification, high-risk only) + F (choreography at scale) + B (big multi-subsystem only). Everything else is rejected as a primary control model — P2P can't bound cost, blackboard-as-control drives conflicts, bidding's overhead waits.

The trust backbone — and this document's own process

The critique-improve loop

Autonomy is only as safe as verification is strong. Every worker's output is gated; the loop below runs inside the fleet and is exactly how this design was hardened — draft, attack, revise, until it stops getting better.

1Automated gates first
Tests, lint, types, build, security. Cheap, objective, fail-closed.
2Structural independence
Maker ≠ checker ≠ tester. No shared history. The critic sees the contract, not the code's reasoning.
3One critic by default
A single diverse-lens critic + the hard test gate. Reserve N-way voting for high-risk — it's the biggest cost driver.
4Know the ceiling
Same-family critics have correlated errors; voting helps less than it looks. False-negatives on subtle bugs run 20–40% — which is why humans stay at the gates.
5Cap at ~3, then escalate
Debugging effectiveness decays fast; the cap kills both wrong output and runaway loops.
6Loop until dry
Keep critiquing until rounds surface nothing material — then stop.

The question the design must answer

The economics, honestly

A fleet job is expensive and buys limited parallelism. That's not a reason to abandon it — it's the reason to be disciplined about when you deploy it.

The bootstrap

At L1 you still pay human review, so the fleet is a latency buyer, not a cost saver — it wins only when work genuinely parallelizes (N ≥ ~3) and finishing faster is worth it. It becomes a cost saver only past L2, where gates drop and human cost falls — which requires your eval to clear the catch-rate thresholds. GO when the task is parallel + well-specified + high-value; otherwise use one interactive agent. Enforce with per-job and global budget ceilings.

The decisive call

What to build

The recommendation

  • Default: Orchestrator–Worker (A), two-tier.
  • Overlays: supervisor-tree (G) for reliability; ensemble/debate (H) for high-risk verification.
  • At scale: event-driven choreography (F).
  • Big multi-subsystem jobs only: hierarchical (B).
  • Durability: pick one engine — Temporal (V2+), LangGraph fine for V1.
  • Verification: auto gates → one diverse-lens critic → human gate backstop.

Tailored to your stack

  • Scala / SBT: the fleet must not run sbt compile — model your compile/verify as a first-class external-verifier node the fleet waits on.
  • Python / uv: workers get the full CI gate — pytest via uv, ruff, mypy.
  • TDD-first, no mocks: maps straight onto "tester writes contract tests first" and the no-mock gate.
  • Vendor-agnostic: LiteLLM for models, MCP for tools, a common adapter for runtimes.
